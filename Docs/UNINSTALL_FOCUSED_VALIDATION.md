## Authorization and isolation prerequisites for real effects

The following is a **plan, not authorization or an executed test**. It requires a separately authorized disposable macOS VM or dedicated sacrificial Mac. Ordinary hosted CI remains synthetic. Runner-preinstalled Homebrew formulae, packages, apps and processes are never removal targets, even if the runner is otherwise ephemeral.

Before setup/removal, record approval of: environment ID and guest OS/build, candidate SHA and artifact hash, signing team, fixture IDs and exact paths/receipts/profile slots, permitted manager setup and helper lifecycle operations, who may approve OS authentication, snapshot/revert scope and evidence destination. Confirm there are no owner files/accounts, shared home directories, host-mounted application folders, synchronized cloud data or production credentials. Use a fresh guest user and a baseline snapshot. Stop on any environment or target mismatch.

Provision supporting managers only in that authorized environment. They are infrastructure, not uninstall targets. Use a separate VM/snapshot per manager where practical, a unique run nonce and fixture namespace such as `mvaudit-<nonce>`. Every removable target must be created for this test run from inspected source. Reject collisions with existing tokens/receipts/paths. Do not select ordinary downloaded applications, free store apps or runner-preinstalled examples as convenient substitutes.

For every scenario:

- Record exact manager/client versions, profile/prefix, package token/version/variants, receipt, canonical paths, code identity and initial file hashes. Maintain an explicit target manifest.
- Create a second test-owned control package/app and data sentinels. Record baseline manager JSON/listings and sentinel hashes; every non-target registration and file must remain unchanged.
- Use the real production app with an isolated guest home, normal execution mode and no mocks. Preview the selected installation and assert mechanism, scope and target before confirming once. Record all prompts and outcomes.
- Independently query the manager and filesystem after completion, after UI verification and after inventory rescan. Exit zero or disappearance from the table is insufficient.
- A failure, changed target, uncertain result or unrelated change stops the scenario. Preserve evidence; do not force, zap, GC, forget receipts, delete manager metadata or retry a different strategy. A repeat starts from a fresh snapshot/new fixture and confirmation.
- Recover/remove only explicitly test-created fixtures inside the guest; prefer restoring the authorized guest snapshot. Never clean the owner's host or a shared/preinstalled manager tree. Do not empty a shared Trash.

## Signed privileged-helper test plan

Use the exact production app/helper identifiers and fixed standard MacPorts prefix inside an approved guest. Build from the candidate SHA. Sign nested code/frameworks and helper before the outer app with matching valid Apple-anchored publisher identity; use hardened runtime and appropriate timestamps for a distributable candidate. Use a dedicated, access-controlled test signing environment/keychain. Do not import signing identities or activate a service on the owner's Mac. The existing ad-hoc unit-test lane remains separate from the signed deployment lane.

Observe request/result logs with no passwords, authorization external-form bytes or signing credentials recorded. Use only test-created port payloads and a test-only authenticated client where protocol-negative tests require it. A second-team case requires a legitimately available second signing identity; lack of one is a missing test, not a reason to bypass peer requirements.

# Security and privacy — Macventory v1.1.0

Macventory discovers software using read-only metadata and typed manager queries under the current user’s permissions. Removal is a separate explicitly confirmed workflow with immutable plans, fresh validation and single-use confirmation. Installation health alone never authorizes removal. No Full Disk Access, password collection or system-protection bypass is implemented.

Production adapters use validated executable paths and structured arguments for official Homebrew, MacPorts and supported mutable-profile Nix operations. Native bundle-only removal uses recoverable Trash after independent ownership/protection/path/process checks. Trusted vendor/Steam handoffs return waiting, not successful removal. Discovery never executes package scripts or registers services. A failed strategy never triggers a filesystem fallback. There is no force, zap, automatic dependency removal, garbage collection or unreviewed data sweep.

The narrowly scoped **MacPorts authorization helper** is the only privileged route in v1.1.0. It requires an Apple-anchored signed app and matching-team packaged helper, uses normal Service Management approval, enforces both peer signing identities through XPC, accepts only exact port/version requests with bound fingerprints and repeats validation. Each request also needs an OS Authorization Services administrator right, checked without daemon interaction before preflight and immediately before the privileged effect. Background-helper approval alone grants no removal authority. Trusted MacPorts paths/ancestors reject unsafe ownership, modes and extended ACLs. It exposes no arbitrary command/file/process operation. Approval is disclosed as persistent background-helper permission, revocable in Login Items. Nothing is queued while approval is pending; a new preview is required afterwards. Ad-hoc local builds cannot use this route for root-owned ports. No helper service was registered or launched during QA.

Queries and effects have bounded waits, output/evidence limits and cancellation handling. A submitted external effect may finish after cancellation; errors do not imply rollback. Tests call production adapters only through fake effects and disposable registries; native Trash, actual manager removal and real vendor launches remain untested. See [current removal support](Docs/UNINSTALL.md) and [the historical independent audit](Docs/UNINSTALL_FINAL_AUDIT.md).

Inventory data stays on the machine. Cache, bounded identity/name history and confirmed-removal records are application-owned; naming history does not establish ownership or uninstall evidence. Diagnostic export is user initiated and contains only source counts/status. Full development inventory exports may contain sensitive paths and names. Inventory discovery requires no network; opening official guidance explicitly performs an ephemeral HTTPS HEAD/redirect check before browser navigation. Confirmed managers/vendor tools have their own behavior.

Leftover Data and Clear App Data require exact-path review and explicit acknowledgment. Leftover Data cleanup is confirmed separately from uninstall. Possible/personal folders require individual selection; shared/protected targets stay blocked. Personal discovery is off by default and bounded to direct children. Missing targets are not credited as deletions; partial/unknown outcomes never authorize automatic retries. Native Finder Trash is recoverable in intent, but cancellation does not guarantee that a submitted operation stopped.

Treat every installed bundle and manifest as untrusted input. Report reproducible crashes, unsafe path handling, privilege issues, unintended writes or unexpected network access with a minimal sanitized fixture. The [official repository](https://github.com/vadimtanel/MacVentory) is public; a private security contact has not yet been configured; arrange a private channel with the maintainer before disclosing sensitive details. Do not invent a contact address or post secrets publicly.

Ad-hoc signatures are for local/development use, not proof of a Developer ID publisher. Do not weaken Gatekeeper or privacy controls to run a downloaded artifact.

The public screenshot mode (`--demo`) contains only fictional records with no filesystem targets. It bypasses real scanning/cache/preferences, disables cache maintenance, uses in-memory column customization and cannot invoke live removal. Demo records are rejected by the uninstall planner even outside the demo UI.

Macventory 1.1.0 keeps preview separate from execution: native row double-click/Return opens only review, including blocked guidance. The initially unchecked checkbox is tied to the exact plan UUID, not a typed application name. Fresh validation and duplicate/concurrent request rejection remain mandatory. Free/ad-hoc signing remains supported for ordinary development and inventory; the privileged MacPorts route separately requires matching trusted signing. Users may make a supported per-app Gatekeeper exception themselves where available; Macventory never changes quarantine or system security policy.

## Unified uninstall and installation health

Installation health is evidence, not authorization to remove software. Exact manager identity, fresh state, immutable previews and single-use confirmation remain separate from filesystem presence. A missing application can permit a verified manager operation, but never an inferred bundle deletion. CLI-only packages do not require an app. Historical receipts and incomplete scans cannot establish installed payloads.

Homebrew execution uses structured arguments, checked standard manager paths, fresh receipt/configuration/executable/artifact fingerprints and independent outcome verification. Only reviewed declarative app/font/owned-binary mappings and narrowly reviewed exact-ID quit effects are automated; privileged or broader hooks use official guided handoff. No force, zap, autoremove, broad cleanup, dependency overrides or manager metadata edits are used. Current running-bundle paths and protected filesystem locations are blocked independently of publisher names.

Vendor tools require an Apple-anchored valid signing chain, matching publisher team and fresh target/tool identity. Interactive launch is Waiting for User, never proof of removal. Official documentation is fixed HTTPS with provider-bound redirect validation; webpage text is never executed. See [trust boundaries](Docs/UNINSTALL.md) and [unverified scenarios](Docs/UNINSTALL_FOCUSED_VALIDATION.md). Real destructive provider validation remains a disposable-environment release gate.
